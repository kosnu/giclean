# `wt-prune`: 消失した worktree の登録だけを整理する

```sh
giclean wt-prune -d 3 --dry-run
giclean wt-prune -d 3 --execute
```

`wt` とは独立した opt-in 操作です。`-d` / `--days` または `-h` / `--hours` で正の待機時間を指定し、`--dry-run` か `--execute` を明示します。固定の「5日」ルールはありません。待機時間は登録メタデータの最終更新から測り、PR のマージ日時ではありません。期間未満のものを強制削除するフラグはありません。

Git が `prunable` と報告する登録だけが対象です。実体ディレクトリが残っていても、その中のファイルは削除しません。ブランチを削除せず、fetch や退避用 ref 作成も行いません。コミットオブジェクトを直接削除することもありません。

## 保留条件

- 選択した待機時間に満たない登録。
- 登録の HEAD、ORIG_HEAD、HEAD reflog のコミットが、保持する ref から到達可能だと確認できない場合。squash や履歴書き換えで内容が同じでも、到達可能性がなければ保留します。
- ステージ済み変更、欠落・破損・読み取り不能の登録 index、不明な操作状態、壊れたメタデータ、シンボリックリンク、解釈できない Git 出力。
- 登録の検査では `GIT_INDEX_FILE` 等の継承されたリポジトリ固有設定で別の index / メタデータへ向かわないよう、登録自身の index と Git ディレクトリに明示的に固定します。コマンド全体の対象リポジトリ指定は維持します。
- Git の一覧・登録ディレクトリ・prune の dry-run に食い違いがある場合。

Git の prune はリポジトリ全体を対象とするため、prunable 登録に一つでも保留対象があれば **全件を保留** します。安全な分だけを指定して Git が別の登録まで消すことを避けるためです。通常の有効な登録や locked 登録は残します。execute 直前に一覧・ファイル内容/更新日時・ref 名/OID・Git dry-run を再検証し、実行後の一覧も確認します。

Git に原子的な対象指定 prune API はありません。実行中は別プロセスの Git 操作・worktree 作成/移動を止めてください。再検証と Git 実行の間の競合を完全には排除できません。

## 保留されたら

期間未満なら指定期間を待って再確認します。未保全コミットなら、何の作業かを調べ、必要な変更を保持するブランチ等へ明示的に保存・検証してから再実行してください。このコマンドは保留を迂回したり、自動で履歴を書き換えたりしません。破損した登録は Git の修復手順を個別に検討します。

初版は単一リポジトリのテキスト出力のみで、batch / JSON 出力は対象外です。GitHub 接続や gh は不要です。
